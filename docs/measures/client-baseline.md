# Client baseline B: frame time at 38 and 72 tiles

Measured on 2026-10-06, on the owner's Mac, in headed Chrome with the GPU. Track CLIENT, objective 1,
part B. Observations only: nothing was optimised.

## Result in one paragraph

On this machine (Apple M2 Max, 120 Hz built-in display) the current client holds 120 fps on both
boards along a scripted camera path: frame interval p95 9.2 ms, no frame over 1.5 refresh intervals.
The estimated target of the programme (p95 <= 16.7 ms at 72 tiles) is therefore **already met here**,
and a requestAnimationFrame figure cannot show more, because it is capped by the refresh rate. The
cost is elsewhere: about 1.0 M (38 tiles) and 1.7 M (72 tiles) triangles and 147 / 207 draw calls
per frame, 3.3 ms of GPU time and 0.9 ms of CPU time per frame at 72 tiles, and a time to interactive
dominated by building the tiles (1.4 s at 72 tiles, of which two thirds is `EdgesGeometry`). These
scale with the number of tiles and will matter on weaker GPUs and phones, which this baseline does
not cover (see Limits).

## Method

- **Board**: a recorded board, not a live deployment (decision of the track, 2026-10-06): no network,
  no Torii, no node. Two fixtures of exactly 38 and 72 tiles in
  `packages/game-core/bench/fixtures/`, generated by `packages/game-core/bench/generate-boards.ts`
  from the fixed seed `0xc0ffee` through game-core: tiles come from the base deck (shuffled), are
  placed on a free slot next to the board with an orientation whose touching edges all match
  (`Layout.isCompatible`, as `Game.tsx` does), a tile that fits nowhere is discarded. Six characters
  stand on legal spots. `packages/game-core/__tests__/bench-boards.test.ts` checks counts, legality,
  and that the committed JSON is what the generator produces.
- **Bench page**: `packages/app-web/bench.html` (`?bench=38|72`), built alone by
  `vite.bench.config.ts` so the shipped app does not carry it. It renders the fixture through the
  game's own path: `GameCanvas` -> `GameScene`, the same assets, materials, shadows, bloom/vignette
  effects and `play` camera. Like in the game, the board arrives after the scene is ready. Only the
  chain layer is bypassed (character rows go through the real `toRenderCharacters`).
- **Camera path** (`src/bench/camera-path.ts`, a pure function of time, 20 s): one zoom from the
  default distance (240) to 60 and back, a pan across the board and two tilts to the steepest angle
  the `play` camera allows. It drives the camera the way input would; `OrbitControls.update()` then
  detects the change and the scene renders every frame. `play` mode forbids orbiting, so the path
  zooms, pans and tilts instead.
- **Counters**: the renderer got a read-only `GameScene.setFrameObserver` (called before a render and
  after every loop tick); rendering is unchanged (`game-scene-frame-observer.test.ts`). Per frame:
  - *frame interval*: delta between successive requestAnimationFrame timestamps;
  - *CPU per frame*: time of the render-loop tick (controls, billboards, composer submission);
  - *GPU per frame*: `EXT_disjoint_timer_query_webgl2` around the render (exposed by this Chrome);
  - *draw calls and triangles*: `renderer.info` summed over all passes of a frame (shadow map, scene,
    bloom, vignette; `autoReset` is turned off and reset per frame);
  - *JS heap*: `performance.memory.usedJSHeapSize` (Chrome run with `--enable-precise-memory-info`);
  - *time to interactive*: navigation start to the end of the first rendered frame that holds every
    tile. Input is bound by `GameScene.init()`, which has finished by then.
- **Driver** (`scripts/bench/run.ts`, Playwright on the installed Google Chrome, headed, not
  headless): per board one warm-up run and 5 measured runs, each in a fresh browser context, served
  from a local static server over the production build. The machine is kept awake with `caffeinate`.
  Percentiles are nearest-rank.
- **CPU profile**: one extra 72-tile run with the CDP sampling profiler (200 us), on a build made for
  the profile (not minified, without the wasm/top-level-await plugins whose transform breaks
  sourcemaps; `BENCH_PROFILE=1` in `vite.bench.config.ts`). The load phase and the camera path are
  profiled separately.

## Rerun

```sh
bun install --frozen-lockfile        # once, at the root (bun 1.3.1; see packages/README.md)
cd packages/app-web
bun run bench                        # builds, measures, writes docs/measures/client-baseline/
bun run bench --profile              # also the CPU profile of one 72-tile run
```

`bun run bench` installs the driver's own two dependencies (`scripts/bench/package.json`, outside the
root workspaces, so the client's frozen lockfile is untouched), builds `dist-bench`, and needs Google
Chrome installed and the display awake with the window visible (a hidden or locked window stops
requestAnimationFrame; the driver then fails after a timeout). Options: `--sizes 38,72 --runs 5
--warmup 1 --duration 20000 --window 1440x900 --no-build --out <dir>`. `--profile-only` runs the profile
alone. The unit tests of the pieces: `bun run test --filter @paved/game-core | @paved/renderer | @paved/app-web`.

## Machine

Mac14,6, Apple M2 Max (12 cores, 38 GPU cores), 64 GB, macOS 27.0.1 (26A434), on AC power. Google
Chrome 154.0.8037.98, WebGL 2 through ANGLE Metal (`ANGLE (Apple, ANGLE Metal Renderer: Apple M2 Max)`),
so a real GPU. Window 1440 x 900 on the built-in Liquid Retina XDR display (3456 x 2234, 1728 x 1117
at 120 Hz); two 60 Hz external displays were attached. The idle refresh interval measured by the page
is 8.3 ms: 120 Hz. `devicePixelRatio` is 2, but the renderer clamps its pixel ratio to at most 1, so
the canvas is 1440 x 813 pixels. The Mac was not otherwise idle (a desktop session with other
applications; load average about 4 before the runs). Full details: `client-baseline/machine.json`.

cross-origin isolation), hence the 9.2-9.4 ms figures for what is a 8.3 ms cadence plus jitter.

## Top costs observed

From the CPU profile of one 72-tile run (`client-baseline/cpu-profile-summary.json`, which has the
top 30 functions by self and inclusive time) and the counters above. Observations, not fixes.

1. **Building the tiles dominates the load.** In the load phase (2.1 s sampled, 0.5 s idle),
   `TileRenderer.createVoxelTile` takes 1.33 s inclusive. `new EdgesGeometry(...)` inside it is 1.07 s
   (about half of the whole load phase); the per-tile clone of geometry and materials
   (`AssetLoader.getModel`) is the rest. This is why time to interactive grows from 0.87 s to 1.42 s
   between 38 and 72 tiles.
2. **Geometry is per tile, not shared.** 72 tiles produce 175 three.js geometries and 207 draw calls
   per frame; triangles per frame are 1.7 M, counting the shadow pass, the scene pass and the edge
   lines. There is no instancing or merging.
3. **The render loop is CPU-cheap but not free.** Over the 20 s path the loop tick takes 2.2 s of
   main-thread time (about 11 %, 0.9 ms per frame); 88 % of the main thread is idle. Inside it:
   `WebGLRenderer.renderBufferDirect` 1.36 s inclusive, `setProgram` 0.68 s (uniform uploads and
   material state per draw), the shadow-map pass (`WebGLShadowMap.render`) 0.47 s, the bloom pass
   0.2 s. The shadow pass draws every tile a second time (2048 x 2048 map).
4. **GPU time follows the triangle count**: 2.6 ms (38 tiles) to 3.3 ms (72 tiles) at p50, 4.5 to 5.0 ms
   at p95, at a canvas of 1440 x 813.
5. **Heap**: 128 MB at interactive for 72 tiles (from 83 MB for 38), down to 92 MB once the load
   garbage is collected.
6. **Every tick renders while the camera moves.** `Game.tsx` also re-renders its React tree on every
   Torii poll; that cost is not in this baseline (no polling here).

## Limits

- One machine, one very strong GPU, one 120 Hz display. The M2 Max hides what a weaker GPU or a phone
  would show; the next step could rerun at CDP CPU throttling and a smaller canvas, and on another
  machine. A rAF figure cannot exceed the refresh rate, which is why CPU and GPU time are reported.
- The Mac was in normal use during the runs (load average about 4); spreads are small (see ranges),
  but this is not a quiet-lab figure.
- Assets are served from localhost, so time to interactive excludes network transfer (15 MB of
  models and 11 MB of textures in the build). The first load after a build also pays shader
  compilation; the warm-up run absorbs it (a first, cold smoke run took 3.0 s to interactive).
- One camera path in `play` mode: no `showcase` profile (more bloom, optional SSAO), no pointer
  input, no hover preview, no UI overlay, no polling, no live updates. Latency from move to display
  is not measured (needs a live node).
- The profile build differs from the measured build (see Method); only function names are meant to
  be read from it. One profile run hung once (Chrome idle for 11 minutes, probably a hidden or locked
  window); it was killed and rerun, and the driver now times out instead of waiting.
